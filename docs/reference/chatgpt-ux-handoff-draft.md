# เกมสดเพื่อเห็นความเข้าใจผิดของนักเรียน — UX handoff ฉบับรอเอกสารต้นทาง

> สถานะ 26 ก.ย. 2026: ยังไม่พบ `00-decision-review.md`, `01-product-brief.md` และผลวิจัยจาก Grok ในไฟล์ที่เข้าถึงได้ คะแนนและข้อสรุปด้านความต้องการจึงเป็น **Assumption / Unknown** เท่านั้น ต้องทบทวนหลังได้รับเอกสาร

## 0. ขอบเขตที่ล็อกแล้ว

- ผู้ใช้กลุ่มแรก: ครูมัธยมรัฐ
- รูปแบบ: เกมสดแบบ Kahoot
- ตัวเลือกผิดแต่ละข้อผูกกับความเข้าใจผิดที่ระบุได้
- รอบซ่อม 3 ข้อ
- ครูอนุมัติ **ทุกข้อ** ก่อนเปิดเกม รวมข้อที่อาจถูกเลือกเข้ารอบซ่อม
- นักเรียนใช้ชื่อเล่นเท่านั้น

**Recommendation:** ออกแบบรอบแรกเป็นเกมที่ครูเตรียมและอนุมัติชุดคำถามกับคลังข้อซ่อมล่วงหน้า ระบบเลือกรอบซ่อม 3 ข้อจากคลังที่อนุมัติแล้วตามคำตอบรวมของห้อง หากคลังยังมีข้อที่อนุมัติไม่ครบ ห้ามเปิดเกม ถ้าไม่มีจุดผิดเด่นชัด ให้ใช้ข้อทบทวนทั่วไปที่ครูอนุมัติไว้ล่วงหน้า

**Assumption ที่ต้องทดสอบ:** เกมหลักมีอันดับ ส่วนรอบซ่อมไม่คิดอันดับ เพื่อลดแรงกดดันเวลาทบทวน; จอ host แสดงข้อมูลรวม ไม่เปิดเผยว่าใครตอบผิด; เครื่องมืออาจช่วยร่างคำถาม แต่ข้อความทุกข้อยังเป็นร่างจนกว่าครูจะอนุมัติ

## 1. ชื่อแบรนด์

| ตัวเลือก | Tagline ภาษาไทย | เหตุผล |
|---|---|---|
| **จับจุด** (แนะนำ) | เล่นจบ เห็นจุดที่ควรทบทวน | สั้น จำง่าย และสื่อผลที่ครูนำไปใช้ต่อ |
| เห็นคำตอบ | เกมในห้องเรียนที่ช่วยเห็นความเข้าใจ | อธิบายหน้าที่ตรงตัว แต่อาจกว้าง |
| เล่นแล้วรู้ | ตอบสนุก แล้วรู้ว่าควรสอนต่อจุดไหน | เป็นกันเอง แต่สื่อบทบาทครูน้อยกว่า |

ชื่อเป็นเพียงตัวเลือกสร้างสรรค์ ยังไม่ได้ตรวจความซ้ำ ชื่อโดเมน หรือเครื่องหมายการค้า

## 2. Interview guide: ครูมัธยมรัฐ 10 ข้อ แบบ JTBD

ผู้สัมภาษณ์ขอให้ครูเล่าเหตุการณ์จริงครั้งล่าสุด ถามต่อว่า “ตอนนั้นทำอย่างไร” และ “มีตัวอย่างให้ดูไหม” โดยยังไม่เสนอเกมนี้ก่อนช่วงท้าย

1. นึกถึงคาบล่าสุดที่คุณอยากรู้ว่านักเรียนเข้าใจบทเรียนแค่ไหน ตอนนั้นสอนเรื่องอะไร และอะไรทำให้ต้องตรวจความเข้าใจ?
2. ก่อนคาบนั้น คุณเตรียมคำถามหรือกิจกรรมตรวจความเข้าใจอย่างไร ใช้เวลาตรงไหนมากที่สุด?
3. ระหว่างคาบ คุณดูจากอะไรว่าเด็กเข้าใจหรือกำลังสับสน? เล่าเหตุการณ์หนึ่งที่จำได้
4. เมื่อเด็กตอบผิด คุณแยกได้อย่างไรว่าเขาเดา อ่านโจทย์พลาด หรือเข้าใจเนื้อหาคลาดเคลื่อน?
5. ครั้งล่าสุดที่พบคำตอบผิดซ้ำกันหลายคน คุณทำอะไรต่อในคาบนั้น และอะไรทำให้เลือกวิธีนั้น?
6. หลังคาบ คุณเก็บหรือทบทวนผลคำตอบอย่างไร ข้อมูลส่วนไหนใช้สอนต่อได้จริง?
7. เล่าครั้งล่าสุดที่ใช้เกมหรือกิจกรรมตอบคำถามสด ขั้นตอนใดลื่นไหล และขั้นตอนใดติดขัด?
8. ถ้าจะใช้คำถามที่ผู้อื่นหรือเครื่องมือช่วยร่าง คุณตรวจอะไรทีละข้อก่อนให้เด็กเห็น? เคยพบข้อที่ต้องแก้อย่างไร?
9. ในห้องที่คุณสอนจริง นักเรียนเข้าร่วมกิจกรรมผ่านมือถืออย่างไรเมื่ออุปกรณ์หรืออินเทอร์เน็ตไม่พร้อม?
10. จากคาบที่เล่ามา ถ้าคุณมีข้อมูลเพิ่มเติมเพียงอย่างเดียวเพื่อวางแผนคาบถัดไป คุณอยากเห็นอะไร และจะใช้ตัดสินใจอย่างไร?

**คำถามติดตาม:** ขอดูตัวอย่างคำถาม/ผลแบบไม่ระบุตัวเด็ก, ใครมีส่วนอนุมัติการใช้เครื่องมือ, เวลาเตรียมและเวลาสอนจริง, วิธีแก้เมื่อเด็กเข้าร่วมไม่ได้, เครื่องมือเดิมที่ใช้และเหตุผลที่ยังใช้ต่อ

### ข้อความขอผลเกมจริงสำหรับ concierge test

> สวัสดีค่ะ/ครับ กำลังทดสอบวิธีช่วยครูดูว่าคำตอบผิดแต่ละตัวเลือกสะท้อนความเข้าใจจุดไหน เพื่อนำไปวางรอบทบทวนสั้น ๆ หลังเกม ถ้าครูสะดวก ขอผลจากเกมตอบคำถาม **หนึ่งคาบที่เล่นจริง** ได้แก่ โจทย์และตัวเลือก เฉลย จำนวนคำตอบในแต่ละตัวเลือก และคำอธิบายหรือบันทึกที่ครูใช้สอนต่อได้ไหมคะ/ครับ เราจะส่งสรุปจุดที่ควรทบทวนและร่างคำถามซ่อม 3 ข้อกลับให้ครูตรวจ ครูเป็นผู้ตัดสินใจว่าจะใช้ข้อไหน ไม่ต้องส่งชื่อจริง ชื่อเล่น รหัสนักเรียน เบอร์โทร หรือข้อมูลที่ระบุตัวนักเรียนได้ หากไฟล์มีข้อมูลเหล่านี้อยู่ กรุณาลบก่อนส่ง และครูเลือกหยุดการทดสอบหรือไม่ใช้ร่างที่ส่งกลับได้ทุกเมื่อ

**บันทึกก่อนทดสอบ:** ระบุผู้รับผิดชอบไฟล์ วิธีส่งและลบไฟล์ ระยะเวลาเก็บ และขอบเขตการนำผลไปใช้ให้ครูทราบก่อนรับข้อมูลจริง; หากข้อหนึ่งมีคำตอบน้อยจนระบุตัวเด็กได้ ให้รวมผลหรือไม่ใช้ข้อนั้น

## 3. คะแนนไอเดีย 100 คะแนน — ชั่วคราว

**44/100 (ความมั่นใจต่ำ)** เป็นคะแนนความพร้อมของหลักฐานจากข้อมูลที่เห็นในงานนี้ ไม่ใช่คะแนนคุณภาพผลิตภัณฑ์หลังอ่าน research

| มิติ | คะแนน | เหตุผลและสถานะ |
|---|---:|---|
| Problem /15 | 7 | **Assumption:** ครูต้องการรู้ว่าผิดเพราะอะไร แต่ยังไม่มีเหตุการณ์จริงจากสัมภาษณ์หรือไฟล์แนบ |
| Demand evidence /15 | 2 | **Unknown:** ยังไม่เห็นพฤติกรรมใช้จริง การกลับมาใช้ซ้ำ หรือการตัดสินใจจ่าย |
| Customer value /15 | 8 | **Inference:** ผูกตัวเลือกผิดกับจุดเข้าใจผิดและรอบซ่อมอาจช่วยเลือกสิ่งที่จะสอนต่อ ต้องเทียบกับวิธีเดิม |
| Differentiation /10 | 5 | **Inference:** วงจรเกม→แผนที่→รอบซ่อมมีจุดจำได้ แต่ยังไม่มีการเทียบผลิตภัณฑ์ปัจจุบัน |
| Feasibility /15 | 9 | **Assumption:** ทำ prototype ได้ แต่คุณภาพการแท็กความเข้าใจผิดและความเสถียรเกมสดยังไม่พิสูจน์ |
| Business potential /15 | 3 | **Unknown:** ผู้ซื้อ งบ ช่องทาง ต้นทุนส่งมอบ/ดูแล และ willingness to pay ยังไม่ทราบ |
| Strategic fit /10 | 6 | **Inference:** มีโอกาสเป็น mass AI product หากใช้ซ้ำแบบ self-serve ได้ แต่ยังไม่เห็น owner และทรัพยากร |
| Risk control /5 | 4 | **Design intent:** อนุมัติทุกข้อและใช้ชื่อเล่นช่วยลดความเสี่ยงบางส่วน ยังต้องทดสอบการหลุดข้อมูลและคำถามผิด |
| **รวม** | **44/100** | **ทบทวนทันทีหลังอ่านเอกสารทั้งสามรายการ** |

**ทางเลือกหลัก:** concierge test กับครูจริงหนึ่งคาบก่อนสร้างเกมเต็ม ใช้ผลเกมจริงให้คนช่วยจัดกลุ่มความเข้าใจผิดและร่าง 3 ข้อให้ครูอนุมัติ จากนั้นดูว่าครูนำไปใช้สอนต่อจริงหรือไม่

**Trade-off:** ได้หลักฐานงานสอนเร็ว แต่ยังไม่พิสูจน์การเล่นสด ความทนของระบบ และต้นทุนต่อครูเมื่อขยาย

**KPI/guardrail ที่ต้องกำหนดก่อนทดลอง:** ครูนำสรุปไปตัดสินใจสอนต่อหรือไม่, เวลาเตรียม/ตรวจเทียบวิธีเดิม, สัดส่วนข้อที่ครูต้องแก้หรือปฏิเสธ, การตอบรอบซ่อมของห้อง, ข้อมูลนักเรียนที่หลุดเข้ามาโดยไม่ตั้งใจ; เกณฑ์ผ่าน/หยุดและเจ้าของการทดลองยังเป็น **Unknown**

## 4. UX flow

```text
ครู: เริ่มเกม → ระบุหัวข้อ/เป้าหมาย → สร้างชุดคำถามหลัก
     → ตรวจโจทย์/เฉลย/ตัวเลือกผิด/ความเข้าใจผิดที่ผูกไว้/คำอธิบาย ทีละข้อ
     → อนุมัติทีละข้อ → ตรวจคลังข้อซ่อมที่ครอบคลุมจุดที่อาจพบ
     → อนุมัติข้อซ่อมทุกข้อ → ตรวจความพร้อม → เปิด lobby

นักเรียน: ใส่รหัสเกม → ใส่ชื่อเล่น → รอใน lobby → ตอบแต่ละข้อบนมือถือ
          → เห็นสถานะส่งคำตอบ/เฉลยเมื่อครูเปิด → ดูผลท้ายเกม → เล่นรอบซ่อม 3 ข้อ

Host: lobby → คำถาม → ปิดรับเมื่อหมดเวลา/ครูกด → เฉลยและคำอธิบาย
      → Top 5 (ตามจังหวะที่ครูกำหนด) → podium เกมหลัก
      → แผนที่ความเข้าใจผิดแบบรวม → เลือกรอบซ่อม 3 ข้อจากคลังที่อนุมัติแล้ว
      → เฉลยรอบซ่อม → สรุปหลังเกมสำหรับครู
```

**กฎป้องกัน:** ปุ่ม “เปิดเกม” ใช้ไม่ได้จนทุกข้อหลักและทุกข้อในคลังซ่อมที่ระบบอาจเลือกมีสถานะอนุมัติ; การแก้ข้อหลังอนุมัติทำให้สถานะกลับเป็น “รอตรวจ”; ถ้าไม่มีข้อซ่อมที่อนุมัติพอสำหรับ 3 ข้อ ระบบขอให้ครูเตรียมเพิ่มก่อนเปิดเกม; เกมใช้ชื่อเล่นเท่านั้นและรายงานสาธารณะเป็นข้อมูลรวม แผนที่ต้องแสดงฐานนับของแต่ละข้อและไม่รวมร้อยละข้ามข้ออย่างคลุมเครือ

| ห้องยังไม่เปิด | เกมนี้ยังไม่เปิดให้เข้าร่วม | `ลองอีกครั้ง` |

## 6. Game feel และ reduced motion

- **เสียง:** เริ่มเกมมีสัญญาณสั้นหนึ่งครั้ง; ช่วงใกล้หมดเวลามีจังหวะเตือนที่ไม่ถี่; เฉลยใช้เสียงสั้นคนละแบบกับการนับถอยหลัง; รอบซ่อมใช้เสียงสงบกว่าเกมหลัก เสียงออกที่จอ host เท่านั้น ครูมีปุ่ม `เปิดเสียง`/`ปิดเสียง` ที่เห็นชัด และค่าเริ่มต้นเสนอให้ปิดเสียงไว้ก่อน (**Assumption** ต้องทดสอบในห้องจริง)
- **Motion:** ตัวเลือกตอบมีการยืนยันด้วยสี/ขอบ/ข้อความ ไม่พึ่งการขยับ; ตัวเลขเวลาเปลี่ยนแบบนิ่ง; Top 5 เลื่อนอันดับสั้น ๆ; podium ปรากฏทีละลำดับโดยไม่กระพริบ; แผนที่แสดงแท่งจำนวนคำตอบแบบไม่ต้องวิ่งยาว
- **จังหวะ:** ครูควบคุมเริ่มข้อ เปิดเฉลย และไปต่อ; ระบบปิดรับตามเวลาที่ตั้ง; หลังเฉลยพักให้ครูอธิบายได้ก่อนกดต่อ; หลังเกมหลักแสดง podium แล้วค่อยเปิดแผนที่และรอบซ่อม 3 ข้อ
- **Reduced motion:** เคารพค่าลดการเคลื่อนไหวของอุปกรณ์ และมีตัวเลือก `ลดภาพเคลื่อนไหว`; แทน animation ด้วยการเปลี่ยนสถานะทันที; ปิดเอฟเฟ็กต์กระเด้ง/ซูม/กระพริบ; คงข้อความ สัญลักษณ์ และลำดับเหตุการณ์เดิม
- **ทางเลือกเมื่อไม่มีเสียง:** ทุกสัญญาณเสียงมีข้อความบนจอ เช่น `เริ่มแล้ว`, `เหลือเวลา`, `หมดเวลา`, `เปิดเฉลย`; ครูปิดเสียงได้โดยเกมยังใช้ครบ
